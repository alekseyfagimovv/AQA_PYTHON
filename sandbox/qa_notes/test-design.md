# Конспект: Тест-кейс vs Чек-лист + JWT (истёкший токен)

## 1. Критерий выбора: Тест-кейс или Чек-лист?
**Главное правило:** Критичность — это НЕ критерий выбора. Критичность — это причина, почему нам важна детализация. 
Критерий: **Нужна ли полная воспроизводимость и передача?**
*   **Тест-кейс:** Максимум деталей (Предусловие, Шаги, Ожидаемый результат, Постусловие). Для регресса, аудита, передачи другому. Время: 15-30 мин.
*   **Чек-лист:** Минимум слов, но максимум конкретики. Одна строка, строго бинарно (Pass/Fail). Для смоука, быстрой проверки. Время: 5 мин.

## 2. Главные ловушки (на чем я поплыл)
*   ❌ **Смешивание уровней (UI vs API).** В чек-листе для API не может быть слов "открыть страницу", "ввести в поле". Только HTTP-метод, эндпоинт и payload.
*   ❌ **Размытость в чек-листе.** Писать "проверить валидацию" или "проверить БД" — нельзя. Должно быть: `Какие данные подаем -> Что конкретно ждем в ответе`.
*   ✅ **Правильный чек-лист (API):** `POST /login, payload: {"pass": "' OR 1=1--"} -> ожидаем статус != 200, токен не выдан`.
*   ✅ **Правильное предусловие (API):** Замокать время (`freezegun`) или сгенерировать JWT с `exp` в прошлом.

## 3. JWT (минимум для тестировщика)
*   Структура: `header.payload.signature` (через точку).
*   Срок жизни лежит в **payload** в поле **exp** (unix-время в секундах).
*   Сервер сравнивает `now()` и `exp`. Если `now > exp` -> возвращает **401 Unauthorized**.
*   *Как тестировать:* Не ждать неделю! Использовать библиотеку `PyJWT` для генерации токена с `exp = now - 60` или `freezegun`.
